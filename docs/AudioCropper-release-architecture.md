# AudioCropper 发布架构设计

> 文档状态：设计中\
> 阶段：产品与技术设计，暂不编码\
> 文档范围：Windows 发布架构、依赖打包、安装、升级、卸载与发布验收

## 1. 项目目标

AudioCropper 是一款面向 Windows
的轻量级离线音频分割工具。用户选择本地音频文件，设置分段时长或片段数量，程序完成切割并将结果保存到源文件所在目录下的同名文件夹。

本文件定义发布与部署方案，不代表相关功能已经实现或经过实测。

### 1.1 已确定的发布要求

-   支持 Windows x64 与 Windows ARM64。
-   两种架构分别提供独立的 EXE。
-   每个 EXE 均支持直接运行和内置安装模式。
-   用户无需预先安装 .NET 或 FFmpeg。
-   尽可能广泛地支持音频容器、解码器和编码器。
-   核心音频处理功能离线运行。
-   尽量减少安装步骤、后台服务和系统级修改。
-   暂不进入编码阶段。

### 1.2 建议技术路线

  层次         建议方案
  ------------ -------------------------------
  编程语言     C#
  桌面界面     WinForms
  应用运行时   .NET 自包含发布
  音频处理     FFmpeg
  发布形式     架构独立的单 EXE
  安装方式     EXE 内置安装流程
  临时文件     用户可写的临时目录
  发布校验     SHA-256；正式发布建议代码签名

Native AOT
可作为评估选项，不作为当前强制要求。应通过实际构建测试比较普通 .NET
自包含单文件与 Native AOT 的兼容性、体积、启动速度和维护成本。

## 2. 发布产物

### 2.1 产物结构

建议每个正式版本至少发布以下文件：

``` text
AudioCropper-vX.Y.Z/
├── AudioCropper-win-x64.exe
├── AudioCropper-win-arm64.exe
└── SHA256SUMS.txt
```

其中两个 EXE 分别面向对应的 Windows CPU
架构。校验文件用于验证下载文件是否完整。

不应将 x64 EXE 标记为 ARM64
原生版本，反之亦然。下载页面应清楚说明适用架构。

### 2.2 单 EXE 的定义

"单
EXE"指用户下载和启动应用时只需要取得一个主程序文件，不要求用户另外下载运行时或
FFmpeg。

这不意味着运行期间绝不产生其他文件。应用可能需要：

-   将嵌入的原生音频组件释放到临时目录；
-   在临时工作目录中生成待处理音频片段；
-   在安装模式下写入安装目录、快捷方式和卸载信息；
-   在用户数据目录中保存设置和必要日志。

这些文件应有明确用途、位置和清理规则。

## 3. 应用内部架构

建议按职责划分逻辑模块，但不要求每个模块独立发布为 EXE。

``` text
AudioCropper.exe
│
├── 启动与模式判断
│   ├── 架构与系统环境检查
│   ├── 版本信息
│   └── 运行模式判断
│
├── 桌面界面
│   ├── 文件选择与拖放
│   ├── 分段参数设置
│   ├── 输出格式设置
│   └── 进度与结果展示
│
├── 音频处理模块
│   ├── 媒体信息读取
│   ├── 格式与编码能力检测
│   ├── 时间边界计算
│   ├── FFmpeg 调用
│   └── 输出验证
│
├── 安装管理模块
│   ├── 安装
│   ├── 升级
│   └── 卸载
│
└── 安全与恢复模块
    ├── 临时目录管理
    ├── 文件冲突检测
    ├── 失败清理
    └── 日志记录
```

模块之间应通过清晰的接口协作。界面不应直接承担复杂的 FFmpeg
参数拼接、文件覆盖和回滚逻辑。

## 4. FFmpeg 依赖打包

### 4.1 总体要求

FFmpeg 作为音频处理核心，随对应架构的 EXE
一起分发。用户正常使用时不需要自行安装 FFmpeg，也不应依赖系统 PATH
中恰好存在的 FFmpeg。

x64 和 ARM64
必须分别使用匹配架构的原生构建。不得在一个架构版本中误打包另一架构的原生二进制。

### 4.2 格式支持策略

"尽可能广泛"应通过明确的构建配置实现，而不是仅凭 FFmpeg
名称推断支持范围。

需要分别核实：

-   输入容器及解复用器；
-   音频解码器；
-   输出容器及复用器；
-   音频编码器；
-   外部库及可选编解码组件；
-   各组件的架构兼容性和许可证。

容器格式与音频编码是不同概念。支持某种容器不代表支持其中所有编码；支持解码也不代表一定支持编码输出。

正式发布前应生成实际能力清单，并通过代表性样本测试。界面只应提供当前构建确实支持的输出格式。

### 4.3 嵌入与释放策略

建议评估将 FFmpeg 可执行文件或必要原生组件嵌入主
EXE，并在运行时释放到应用专用临时目录的方案。

释放过程应满足：

1.  先校验嵌入资源的版本和 SHA-256。
2.  使用应用专用目录，避免与其他软件共享可变文件。
3.  防止路径穿越、意外覆盖和不可信文件替换。
4.  确认释放文件与当前进程架构匹配。
5.  释放失败时停止处理并给出明确错误。
6.  仅清理由本程序创建且确认不再使用的临时组件。

也可以评估直接使用 FFmpeg 原生库的方案，但必须验证 .NET
发布方式、原生依赖加载、许可证和升级维护成本。

### 4.4 许可证合规

FFmpeg
的许可证及义务取决于具体版本、配置选项和启用的外部组件。发布前必须：

-   固定 FFmpeg 版本和构建来源；
-   保存完整构建配置；
-   检查 LGPL、GPL 及其他第三方组件的适用条款；
-   随软件提供要求提供的许可证和声明；
-   按适用许可证履行对应的源码提供或获取义务；
-   保留第三方依赖清单及版本记录。

不得仅凭"FFmpeg 通常是 LGPL"就认定某个实际构建符合
LGPL。许可证审查应针对最终发布的二进制进行。

## 5. 运行模式

### 5.1 直接运行模式

用户双击 EXE 后直接进入主界面，不要求先安装。

要求：

-   不要求管理员权限；
-   不修改系统 PATH；
-   不默认创建开机启动项；
-   不默认安装 Windows 服务；
-   不强制写入 EXE 所在目录；
-   在只读目录、U 盘或受限目录中也能妥善处理临时文件；
-   设置、日志和临时文件分别管理。

便携模式下的设置保存位置应在后续产品设计中明确。可考虑提供便携设置选项，但不得未经用户同意在程序目录写入数据。

### 5.2 内置安装模式

用户可从应用界面或启动入口选择安装。安装向导建议包含：

1.  检测 Windows 版本和 CPU 架构；
2.  检查已有安装及运行中的实例；
3.  选择安装目录；
4.  检查目录权限和剩余空间；
5.  校验并准备所需文件；
6.  安装应用文件；
7.  按用户选择创建桌面或开始菜单快捷方式；
8.  注册卸载信息；
9.  验证安装结果；
10. 提供启动应用的选项。

默认优先采用当前用户安装，避免不必要的管理员提权。若将来提供所有用户安装，应明确说明其权限要求和系统范围影响。

## 6. 目录与数据管理

建议区分程序文件、用户设置、日志和临时文件。

  -------------------------------------------------------------------------------------
  数据类型                建议位置                     生命周期
  ----------------------- ---------------------------- --------------------------------
  已安装程序              用户选择的安装目录           升级或卸载时管理

  用户设置                用户配置目录                 默认跨升级保留

  日志                    用户本地应用数据目录         按保留策略清理

  FFmpeg 释放文件         应用专用临时或缓存目录       不再使用时清理

  音频切割工作文件        输出目标附近的临时目录       任务结束后清理或按失败策略保留

  用户源音频              用户原位置                   程序不得修改或删除

  成功导出的片段          源文件同目录下的同名文件夹   由用户管理，卸载不得删除
  -------------------------------------------------------------------------------------

源文件例如：

``` text
D:\Podcasts\lesson.mp3
```

默认输出：

``` text
D:\Podcasts\lesson\
├── 0001.mp3
├── 0002.mp3
└── 0003.mp3
```

目标文件夹已存在时，必须提示用户确认。不得默认清空整个目录。

## 7. 安装冲突与文件安全

当目标输出文件夹已存在时，建议提供：

-   覆盖本次输出涉及的同名文件；
-   创建新的编号目录，例如 `lesson (1)`；
-   取消操作。

覆盖前应显示影响范围。只允许处理本次任务明确生成并登记的目标文件，不得清空整个文件夹。遇到无法确认归属的同名文件，应额外提示并默认保护。

音频切割建议采用临时工作目录：

1.  在目标目录附近创建唯一临时目录；
2.  在临时目录中完成处理；
3.  检查预期文件数量、文件大小和可读取性；
4.  成功后再提交到最终目录；
5.  失败时清理本次产生的文件，并保留必要错误信息；
6.  如果清理失败，提示用户临时目录位置。

若磁盘空间不足、程序异常退出或用户取消任务，不得将未完成结果显示为完整成功结果。

## 8. 升级设计

### 8.1 第一版策略

第一版建议采用手动升级，不引入常驻更新服务。

升级流程：

1.  用户取得新版本 EXE；
2.  校验文件哈希，正式发布后还应验证数字签名；
3.  检查新版本架构是否与当前设备匹配；
4.  检查版本兼容性和当前运行状态；
5.  准备新版本文件；
6.  关闭旧实例；
7.  执行替换；
8.  验证新版本可启动；
9.  失败时恢复旧版本；
10. 保留用户设置、日志策略和音频输出。

### 8.2 数据兼容

-   用户生成的音频不得参与程序升级替换。
-   用户设置应有版本标识和迁移策略。
-   无法迁移的设置应备份，不得直接丢弃。
-   升级失败不能导致用户数据丢失。
-   便携版替换 EXE 时也应提醒用户先关闭程序。

未来如增加自动更新，应要求用户明确启用，并提供更新来源验证、下载校验、失败回滚和版本说明。

## 9. 卸载设计

卸载程序应只删除能够确认属于 AudioCropper 的应用文件和登记信息。

卸载时：

-   删除程序安装目录中的应用文件；
-   删除由安装程序创建的快捷方式；
-   删除对应卸载注册信息；
-   默认保留用户设置或在卸载前询问；
-   保留用户生成的音频文件；
-   不删除源音频；
-   不清理不属于应用的共享依赖；
-   对无法确认归属的文件采取跳过策略。

卸载完成后，应显示未能删除的文件或目录位置，方便用户自行检查。

## 10. 架构、系统与兼容性

### 10.1 CPU 架构

  发布版本    目标设备                    原生依赖
  ----------- --------------------------- ------------
  win-x64     Intel / AMD 64 位 Windows   x64 构建
  win-arm64   Windows ARM64 设备          ARM64 构建

两个版本应分别构建、测试和签名。不能仅通过更改文件名把一个架构的程序伪装成另一个架构。

### 10.2 最低 Windows 版本

最低 Windows 版本尚未确定。正式构建前需要结合所选 .NET 版本、WinForms
API、FFmpeg 构建和目标用户设备确定支持范围。

不得在没有测试的情况下宣称支持所有 Windows 10 或 Windows 11 版本。

### 10.3 系统权限

默认不需要管理员权限。以下操作应避免或明确提示：

-   写入系统目录；
-   修改机器级环境变量；
-   安装系统服务；
-   修改系统级文件关联；
-   安装所有用户可用的快捷方式或注册信息。

## 11. 安全、完整性与发布可信度

建议正式发布时加入：

-   EXE 的 Authenticode 数字签名；
-   发布文件 SHA-256 校验值；
-   第三方依赖及许可证清单；
-   固定且可追溯的构建版本；
-   安装包内资源哈希校验；
-   FFmpeg 调用参数安全处理，避免将用户文件名拼接为不安全的命令；
-   临时目录权限和文件清理检查；
-   不静默下载或执行未经验证的外部程序。

数字签名证书及其成本、申请方式属于发布运营决策，当前尚未确定。

## 12. 构建与发布流程

建议使用可重复、可审计的发布流程：

``` text
提交源代码
    │
    ▼
版本与依赖锁定
    │
    ▼
分别构建 x64 / ARM64
    │
    ▼
生成对应架构 FFmpeg 组件
    │
    ▼
依赖与许可证检查
    │
    ▼
单 EXE 打包
    │
    ▼
恶意软件与安全扫描
    │
    ▼
功能、安装、升级、卸载测试
    │
    ▼
生成 SHA-256
    │
    ▼
数字签名
    │
    ▼
发布 GitHub Release
```

每次发布应保留：

-   源代码版本；
-   构建工具和 SDK 版本；
-   FFmpeg 版本及配置；
-   第三方依赖清单；
-   构建日志；
-   测试报告；
-   最终 EXE 的哈希值；
-   许可证文件。

## 13. 验收标准

  编号   验收项目       通过条件
  ------ -------------- ------------------------------------------------
  R-01   x64 发布       在受支持的 x64 Windows 环境正常运行
  R-02   ARM64 发布     在受支持的 ARM64 Windows 环境原生运行
  R-03   单 EXE 分发    用户只需取得对应架构的主 EXE
  R-04   直接运行       无需安装即可使用核心功能
  R-05   内置安装       可从同一个 EXE 启动安装流程
  R-06   免预装运行时   干净环境无需预装 .NET
  R-07   FFmpeg 打包    无需用户另行安装 FFmpeg
  R-08   格式支持       实际支持范围与发布清单一致
  R-09   离线运行       断网时核心切割功能可用
  R-10   文件安全       不修改源音频，不误删其他文件
  R-11   失败恢复       取消、空间不足和异常中断不会产生虚假的成功结果
  R-12   升级           升级失败能够恢复旧版本
  R-13   卸载           不删除用户源文件和导出音频
  R-14   完整性         发布文件可通过 SHA-256 校验
  R-15   许可证         发布依赖具备对应许可证材料

所有验收项目都需要在实际构建后测试，当前状态为待验证。

## 14. 尚待确定的事项

以下事项不应在缺少讨论或实测的情况下擅自定案：

1.  最低支持的 Windows 版本；
2.  是否采用 Native AOT；
3.  FFmpeg 的具体版本、构建来源和启用组件；
4.  是否启用 GPL 组件，以及相应许可证合规方案；
5.  EXE 体积目标；
6.  安装目录默认值；
7.  便携模式设置保存位置；
8.  日志保留时长和大小限制；
9.  数字签名证书及发布主体；
10. 是否提供自动更新；
11. ARM64 实机测试环境；
12. 旧版本设置迁移规则。

## 15. 当前设计结论

AudioCropper 的发布方案暂定为：

-   Windows x64 与 ARM64 双架构；
-   每个架构独立发布一个主 EXE；
-   同一个 EXE 支持直接运行和内置安装；
-   C# + WinForms；
-   .NET 自包含发布，Native AOT 待评估；
-   FFmpeg 随程序打包，尽可能广泛支持音频格式；
-   核心功能离线运行；
-   默认不要求管理员权限；
-   手动升级，失败可回滚；
-   卸载保护用户生成的音频和源文件；
-   暂不编码，继续完善设计文档。
